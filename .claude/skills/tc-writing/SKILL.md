# TC Writing Skill

이 Skill은 **TC 작성 규칙과 품질 기준**만 정의합니다. TC 생성 Workflow(PRD 확인 → 정보 수집 →
초안 작성 → Spreadsheet 검토용 반영 → 사용자 검토 → 승인 등)는 이 Skill의 책임이 아니며, 이를 사용하는 Agent(예:
`tc-agent`)가 담당합니다. 이 Skill은 특정 프로젝트명, 서비스명, PRD 내용을 알지 못하는 상태를
전제로 작성되었으며, 어떤 QA 프로젝트에서도 동일하게 재사용할 수 있어야 합니다.

## 1. TC 작성 규칙

### 1.1 공통 품질 기준

- 하나의 TC는 하나의 명확한 검증 목적을 가진다. 서로 독립적인 여러 검증 목적을 하나의 TC에
  과도하게 포함하지 않는다.
- 3 Depth는 "무엇을 테스트하는지" 목적이 명확하게 드러나도록 작성한다(2절 3 Depth 작성 규칙).
- Preconditions에는 TC 수행에 반드시 필요한 사전 조건만 작성한다.
- Test Steps는 실제 사용자가 수행 가능한 순서대로 작성한다.
- Expected Result는 실제 테스트 수행 시 Pass/Fail을 판단할 수 있도록 명확하고 관찰 가능한 결과로
  작성한다.
- "정상 동작한다", "문제없다", "~되는가?" 등 모호하거나 판정하기 어려운 표현은 사용하지 않는다.
  (예: "로그인되는가?" 대신 "로그인 성공 후 Home(`/`)으로 랜딩되고 상단 네비게이션이 로그인 상태
  메뉴로 전환된다"와 같이 관찰 가능한 결과로 작성한다.)

### 1.2 요구사항 기반 TC 작성

- PRD에 없는 제품 요구사항이나 기대 동작을 임의로 정의하지 않는다.
- 다만 명시된 요구사항을 검증하기 위한 **Positive / Negative / Boundary Case**는 QA 관점에서
  도출할 수 있다(PRD에 명시된 동작 자체를 벗어나 새로운 기능을 상상하는 것이 아니라, 이미 명시된
  요구사항의 정상/예외/경계 조건을 검증하는 것이므로 허용된다).
- 기대 결과를 PRD만으로 판단할 수 없는 경우 임의로 판단하지 않고 사용자에게 확인한다.
- TC 개수를 늘리기 위한 불필요한 Case 분리를 하지 않는다. 분리·통합은 1.3의 기준으로만 판단한다.

#### Negative / Error Case 도출 기준

Positive Case만 작성하고 Negative Case(예외·에러 케이스)를 누락하지 않도록, 대상 Feature에
실제로 해당하는 항목만 아래 카테고리를 참고해 선택적으로 도출한다(모든 카테고리를 기계적으로
전부 작성하라는 뜻이 아니다).

- 잘못된/유효하지 않은 입력값 (형식 오류, 필수값 누락, 허용 범위 초과)
- 권한/인증 실패 (미로그인, 권한 없음, 세션 만료 등 PRD에 명시된 경우)
- 상태/순서 위반 (선행 조건 미충족 상태에서의 조작, 중복 실행/제출 등)
- 외부 의존성 실패 (네트워크 오류, 서버 오류 등 — PRD 또는 기존 요구사항에 언급된 범위 내에서만)
- 경계값 위반 (Boundary Case와 중복되는 조건은 별도 Negative Case로 다시 만들지 않고 하나로 정리)

Negative Case에도 다음 원칙을 동일하게 적용한다.

- **PRD 범위 제한**: PRD에 없는 에러 메시지 문구, 에러 코드, 시스템 동작을 임의로 창작하지 않는다.
  구체적인 에러 표시 방식이 PRD에 명시되어 있지 않아 판단할 수 없는 경우, 위 "기대 결과를 PRD만으로
  판단할 수 없는 경우..." 규칙에 따라 사용자에게 확인한다.
- **관찰 가능한 Expected Result**: "에러가 발생한다", "실패한다"처럼 모호하게 쓰지 않고, 화면/상태
  변화까지 관찰 가능하게 작성한다. (예: "이메일 미입력 시 실패한다" 대신 "필수 입력값 누락 시
  이메일 입력 필드 하단에 '이메일을 입력해주세요' 오류 메시지가 표시되고 제출 버튼은 비활성화
  상태를 유지한다")
- **과도한 분리 방지**: 동작이 같고 결과 규칙도 같은 유사 에러 조건(예: 여러 필드에서 동일하게
  반복되는 필수값 누락 패턴)은 대표 케이스로 통합하고, 필드마다 TC를 개별로 늘리지 않는다(1.3 통합
  기준과 동일). 동작이 다르면 통합하지 않는다.

### 1.3 세분화 기준 (Granularity)

TC 개수를 목표로 삼지 않되, **서로 다른 사용자 동작은 하나의 TC로 합치지 않는다.** 같은 Feature뿐
아니라 모든 Feature에서 같은 기준을 적용해 TC의 크기가 일관되도록 한다.

**기본 단위: 동작 1개 → 관찰 결과 1묶음 = TC 1개**

- 하나의 TC는 사용자 동작(트리거) 1개와 그 결과를 검증한다. 진입 경로가 다른 경우(예: 검색창
  클릭 / 검색 아이콘 클릭 / 주소창 직접 입력), 이동 동작(뒤로가기, 새로고침 등), 버튼·상태별 동작은
  각각 별도 TC로 작성한다.
- 예시: 검색페이지 진입은 아래처럼 동작별 TC 4개로 작성한다.
  - 상단 검색창 클릭 → 검색페이지 표시, URL `https://store.laftel.net/search`
  - 브라우저 뒤로가기 → 메인페이지 표시 (사전 조건: 검색창 클릭으로 검색페이지에 진입한 상태)
  - 메인페이지 검색 아이콘 클릭 → 검색페이지 표시
  - 주소창에 `https://store.laftel.net/search` 입력 → 검색페이지 표시

**분리해야 하는 경우** — 아래 중 하나라도 서로 다르면 별도 TC로 작성한다.

- 사용자 동작(트리거, 진입 경로 포함)
- 검증 목적(Requirement 또는 검증하는 대상)
- 사전 조건(로그인 여부, 대상 상태, 필요한 데이터)
- 입력 조건의 분류(정상 / 예외 / 경계)
- 실패했을 때 원인을 구분해야 하는 서로 독립된 기대 결과

**통합해도 되는 경우** — 동작이 같을 때만 허용한다.

- 한 동작의 결과로 같은 화면에서 함께 관찰되는 표시 요소들(예: 화면 노출 + URL). Expected Result
  안에서 항목별로 줄바꿈(`<br>`)해 판정한다.
- 같은 동작에 입력값만 다르고 결과 규칙이 같은 단순 반복(예: 여러 필드의 동일한 필수값 누락)은 대표
  케이스 1개로 통합한다. 입력값에 따라 결과 규칙이 달라지면 분리한다. 단, 최대치가 있는 항목의 경계값
  (상한 초과/상한/상한 미만)은 통합하지 않고 1.6에 따라 분리한다.
- 한 동작이 여러 UI 조작으로 이루어지는 경우(예: 키워드 입력 후 Enter)는 하나의 동작으로 본다.

**작성 형식**

- **Test Steps**: 동작 1개(위 기준의 한 동작)만 쓴다. 해당 동작 이전의 진입·준비는 Preconditions에
  쓰며, 이전 동작의 결과가 사전 상태이면 그 상태를 구체적으로 적는다
  (예: `검색창 클릭으로 검색페이지(/search)에 진입한 상태`). Steps는 가급적 1~2단계로 쓴다.
- **Expected Result**: 그 동작의 관찰 결과만 쓰고, 항목이 2개 이상이면 항목별로 Pass/Fail을 판정할
  수 있게 `1.`, `2.` 번호와 `<br>` 줄바꿈으로 구분한다. 표기 방법은 1.5를 따른다.
- Expected Result가 서로 다른 Requirement 여러 개를 섞거나, 실패 시 어느 항목 때문인지 특정할 수
  없으면 분리 대상이다.

### 1.4 일관성 규칙 (Consistency)

- **3 Depth 형식**: `{검증 대상} {검증 목적 분류}` 형태의 짧은 목적 문구로 쓴다(예: `필수 입력값 누락 검증`, `형식 오류 검증`, `성공 케이스`). 같은 분류는 같은
  표현을 쓰며, PRD 표기가 혼용된 경우 한 가지로 통일하고 처음 한 번 PRD 표기를 병기한다.
- **Preconditions 표현**: 같은 상태(예: 로그인, 비로그인, 특정 상품 상태)는 모든 TC에서 동일한
  표현으로 쓴다. 문서 상단 "공통 전제"에 둔 내용은 각 TC에 반복해서 쓰지 않는다.
- **화면 요소·문구**: Expected Result에 쓰는 요소명과 문구는 PRD 표기를 그대로 사용하고, 임의로
  번역하거나 축약하지 않는다.
- **구조의 통일**: 같은 종류의 검증(예: 필수값 누락, 상태별 버튼 표시)은 한 Feature 안에서 같은
  구조(시나리오 문형, 단계 수, 판정 항목 형식)로 작성한다.
- **Priority**: 같은 Risk 항목에 매핑된 TC는 일관된 Priority를 유지한다(3. 참조).

### 1.5 표기 규칙 (Notation)

Test Steps와 Expected Result는 짧고 읽기 쉽게 쓰고, 시트에서 줄바꿈되어 표시되도록 작성한다.

- **간략 표기**: 문장형 종결("~한다", "~된다")을 쓰지 않고 명사형·체언 종결로 간략히 쓴다. 조작 대상은
  `위치 내 요소 동작` 형태로 쓴다. PRD의 요소명·문구는 그대로 유지한다(1.4).
  - 예: `작품 카드(">" 화살표)를 클릭한다.` → `작품 카드 내 ">" 클릭`
  - 예: `검색페이지가 표시되고 URL이 /search로 변경된다.` → `1. 검색페이지 표시<br>2. URL: /search`
- **번호는 실제로 여러 개일 때만**: 항목이 2개 이상일 때만 번호를 붙이고, 단일 항목에는 번호를 붙이지 않는다.
  Test Steps, Preconditions, Expected Result 모두 **`1.`, `2.` 형식**으로 통일하며(`1)` 형식은 쓰지 않는다),
  항목마다 번호를 붙이고 항목 사이를 `<br>`로 구분한다. 번호 없이 `<br>`만으로 나열하지 않는다.
  - **Test Steps** 예: `1. 검색창에 "원" 입력<br>2. 엔터` / 단일: `작품 카드 내 ">" 클릭`
    - 복수 사전 조건 예: `1. 로그인 상태<br>2. 장바구니에 상품 2건 담김` / 단일: `로그인 상태`
    - 복수 기대 결과 예(한 동작에 기대 결과가 2개인 경우, 예: 팝업 닫힘 + 화면 유지):
      `1. 팝업 닫힘<br>2. 상품상세 화면 유지` / 단일: `검색페이지 표시`
    - 한 동작에서 함께 관찰되는 결과(화면 노출 + URL 등)도 2개 이상이면 위 형식을 따른다.
      예: `1. 검색페이지 표시<br>2. URL: /search`
- **줄바꿈**: 번호 항목 사이는 `<br>`로 구분한다. 3 Depth는 한 줄 목적 문구라 번호 항목을 쓰지 않는다. Markdown 표의
  셀은 한 줄이므로 문서에는 `<br>`를 쓰고, Spreadsheet 반영(`append`) 시 `<br>`가 실제 줄바꿈으로
  변환되어 표시된다. `<br>` 외의 태그나 실제 줄바꿈 문자는 문서 표에 쓰지 않는다.

### 1.6 TC 설계 기법 (명세기반 블랙박스)

PRD 명세를 입력으로 하는 블랙박스 기법으로 TC를 도출한다. 먼저 대상 기능을 분류하고 분류별 기법을
적용한다.

| 기능 분류 | 해당 예 | 적용 기법 |
|---|---|---|
| 입출력 기능 | 검색어·폼·수량 등 값을 입력하고 결과를 확인하는 기능 | 정상 동작 / 네거티브 테스트 / 경계값 테스트 |
| 동작 기능 | 버튼·화면 전환·찜/삭제 등 조작과 상태에 따라 결과가 달라지는 기능 | 결정테이블 / 상태전이 / 유스케이스 테스트 |

- **정상 / 네거티브 / 경계값**: 허용 입력, 허용되지 않는 입력(Negative 도출 기준 참조), 상·하한 및
  직전·직후 값을 PRD에 명시된 범위 안에서 도출한다. 최대치가 있는 항목은 아래 "상한 항목 경계값 분리"
  를 따른다.
- **상한 항목 경계값 분리**: PRD에 **최대치(상한 N)가 명시된 항목**(표시 개수, 입력 글자 수, 수량 등)은
  상한 N마다 아래 3개 TC로 분리해 작성한다.
  - **상한 초과**: N을 넘는 조건(예: N+1 이상) → 초과분 처리 결과(PRD에 명시된 대로, 예: "N개까지만 표시")
  - **상한**: 정확히 N → N개 모두 표시/허용
  - **상한 미만**: N보다 작은 값(예: N-1) → 존재하는 개수 전부 표시/허용
  - 예: 자동완성 작품 최대 20개 → `작품 21개 이상 매칭 시 20개만 표시` / `작품 정확히 20개 매칭 시 20개
    표시` / `작품 19개 매칭 시 19개 표시`. 서로 다른 상한(작품 20 / 연관 검색어 10)은 한 TC에 같이
    넣지 않고 **상한 대상마다 3개씩** 작성한다.
  - 세 TC는 입력 조건 분류(초과/경계/미만)가 달라 1.3의 "분리해야 하는 경우"에 해당하며 대표 케이스
    통합 대상이 아니다. 3 Depth에 개수 조건(상한 초과 / 상한 / 상한 미만)이 드러나게 쓴다.
  - Preconditions에 해당 개수를 만족하는 데이터(키워드·상품·수량)를 사전에 확인해 둔다고 구체적으로
    쓴다. 정확히 N개 또는 N-1개를 만족하는 데이터를 확보할 수 없으면 해당 TC를 임의로 만들지 않고
    사용자에게 데이터 확보 방법을 확인한다.
  - PRD 범위 제한(1.2): 상한 초과 시 기대 결과가 PRD에 없으면(예: 글자 수 초과 시 차단/오류 여부)
    초과 TC의 기대 결과를 임의로 정의하지 않고 사용자에게 확인한다. 이 경우 상한/미만 TC는 작성하고
    초과 TC는 보류 사유와 함께 미결 질문으로 남긴다.
- **결정테이블**: 조건(로그인 여부, 상품 상태 등)의 조합에 따라 결과가 달라지면 조건·결과 표로 정리하고
  의미 있는 조합마다 TC를 둔다.
- **상태전이**: 상태(예: 찜 on/off, 선택/해제)와 전이 동작을 정리하고 유효 전이와 PRD에 명시된 무효
  전이를 TC로 둔다.
- **유스케이스**: 사용자 목표 단위의 주요 흐름을 동작 단위(1.3)로 나누어 TC로 둔다.
- 기법으로 도출한 TC도 1.3(동작 1개 원칙)과 1.2(PRD에 없는 기대 결과 임의 정의 금지)를 따른다. 기대
  결과를 PRD로 판단할 수 없으면 사용자에게 확인한다.
- TC 문서에 Feature별 **"기법 적용 요약"** 표(기능 분류 / 적용 기법 / 관련 TC ID)를 두고, 결정테이블·
  상태전이를 쓴 경우 그 표를 함께 싣는다. 컬럼을 추가하거나 3 Depth에 접두어를 붙이지 않는다.

## 2. TC 컬럼 정의

다음 10개 컬럼을 기본 TC Format으로 사용한다. 컬럼 순서는 항상 아래와 같이 고정한다.

| 순서 | 컬럼명 | 설명 |
|---|---|---|
| 1 | ID | TC 고유 ID (3. TC ID Naming Rule 참조) |
| 2 | 1 Depth | 시스템/도메인. 서비스의 큰 기능 단위나 화면 (예: 회원가입/로그인, 결제, 마이페이지) |
| 3 | 2 Depth | 세부 기능/컴포넌트. 1 Depth 안의 구체적인 기능이나 페이지 (예: 이메일 회원가입, 카카오 로그인, 비밀번호 찾기) |
| 4 | 3 Depth | 테스트 시나리오/목적. 무엇을 테스트할지 목적을 명시 (예: 필수 입력값 누락 검증, 형식 오류 검증, 성공 케이스) |
| 5 | Preconditions | TC 수행에 필요한 사전 조건 |
| 6 | Test Steps | 사용자가 수행 가능한 순서의 조작 단계 |
| 7 | Expected Result | 관찰 가능하고 Pass/Fail 판정이 가능한 기대 결과 |
| 8 | Priority | P0 / P1 / P2 (3. Priority/Risk 평가 규칙 참조) |
| 9 | Requirement ID | 연결된 PRD Requirement ID (Priority 뒤에 위치) |
| 10 | Result | Pass / Fail / Blocked / N/A (기본값은 빈 값) |

### 1 Depth / 2 Depth / 3 Depth 작성 규칙

- 1 Depth는 시스템/도메인, 2 Depth는 그 안의 세부 기능/컴포넌트를 적는다. 1 Depth와 2 Depth는
  같은 내용이 들어갈 수 있다(예: 기능이 하나뿐인 화면은 두 컬럼에 같은 값).
- 값은 Feature PRD의 화면·기능 구분과 용어를 그대로 사용하고, 임의의 신조어를 만들지 않는다.
- 같은 기능은 문서 전체에서 항상 같은 표기를 쓴다(1.4 일관성). 표기만 다른 값(예: `자동완성` / `자동 완성`)을 두지 않는다.
- 2 Depth는 "기법 적용 요약"의 기능 분류와 가능한 한 일치시켜 TC와 기법 간 추적이 되게 한다.
- 모든 TC에 1 Depth와 2 Depth를 채운다. PRD만으로 구분이 불명확하면 임의로 정하지 않고 사용자에게 확인한다.
- 3 Depth는 테스트 시나리오/목적이다. 무엇을 테스트할지 목적을 한 줄로 명시한다(예: 필수 입력값 누락 검증,
  형식 오류 검증, 성공 케이스). 형식은 `{검증 대상} {목적 분류}`이며, 목적 분류는 성공 케이스 / 필수값 누락 검증 /
  형식 오류 검증 / 경계값(상한 초과·상한·상한 미만) 검증 / 상태 전이 검증처럼 설계 기법(1.6)과 연결되는 표현을 쓴다.
- 같은 2 Depth 안에서 TC끼리 구분되는 차이(조건, 상태, 입력 분류, 로그인 여부, 개수)는 3 Depth에 드러나게 쓴다.
  세부 조건·관찰 결과는 Preconditions / Test Steps / Expected Result에 쓰고 3 Depth에 길게 풀어 쓰지 않는다.
- 하나의 TC는 하나의 목적만 가진다(1.3). 3 Depth에 서로 다른 목적을 나열하지 않는다.

### 사용자 입력 전용 추가 컬럼

- 프로젝트가 정의한 경우, Spreadsheet의 위 10개 컬럼 뒤에 사용자가 직접 값을 입력하는 컬럼(예: 분류
  표시용 컬럼)이 추가될 수 있다. 이런 컬럼은 TC를 생성하는 Agent가 값을 쓰지 않고 항상 빈 값으로
  생성하며, 값의 의미를 임의로 해석하거나 대신 입력하지 않는다.
- 이 컬럼은 Spreadsheet에만 존재할 수 있으며, TC 문서(Markdown)의 표는 위 10개 컬럼만 사용한다.

### Requirement ID

- 컬럼 위치는 Priority 바로 뒤(9번째)이다.
- PRD에 Requirement ID가 존재하면 해당 ID를 그대로 사용한다.
- PRD에 Requirement ID가 존재하지 않는 경우 임의로 Requirement ID를 생성하지 않는다. 이 경우
  해당 TC의 Requirement ID 컬럼은 기본적으로 빈 값으로 유지한다.
- Requirement Traceability 관리 방식(예: 빈 값 대신 다른 표기를 쓸지 등)에 대한 결정이 필요한
  경우 임의로 정하지 않고 사용자에게 확인한다.

### Result

- TC 생성 시 기본값은 빈 값으로 유지한다.
- 테스트 수행 후 `Pass` / `Fail` / `Blocked` / `N/A` 중 하나를 기록할 수 있는 컬럼으로 정의한다.
- TC를 생성하는 Agent는 테스트를 실제로 수행하는 Agent가 아니므로, Result 값을 임의로 입력하지
  않는다.

## 3. Priority / Risk 평가 규칙

각 TC가 검증하는 요구사항 또는 사용자 시나리오의 Risk를 평가하여 Priority(`P0`/`P1`/`P2`)를
결정한다.

### Risk Score

```
Risk Score = Impact × Likelihood
```

#### Impact / Likelihood 점수 기준

Impact(결함 발생 시 사용자/서비스 영향)와 Likelihood(결함 발생 가능성)의 리스크 팩터와 1~5점
기준은 이 Skill에서 정의하지 않는다. 사용자가 제공한 **리스크 산정 절차 문서**(리스크 평가 요소,
점수 기준, 레벨 결정 방식을 정의한 문서)를 읽기 전용 참고자료로 조회해 그 기준을 따른다. 이 문서의
위치(예: 어떤 Spreadsheet의 어떤 탭)는 이 Skill을 로드한 Agent가 지정한다. 절차 문서를 확보할 수
없으면 Impact/Likelihood를 임의로 산정하지 않고 사용자에게 확인한다.

#### Priority 매핑

| Priority | Risk Score 범위 |
|---|---|
| P0 | 16 ~ 25 |
| P1 | 9 ~ 15 |
| P2 | 1 ~ 8 |

### Priority 평가 원칙

- Impact와 Likelihood는 단순 추측으로 결정하지 않으며, 리스크 산정 절차 문서의 점수 기준에 따라
  결정한다.
- PRD의 기능 중요도, 변경 범위, 사용자 조건, 데이터 흐름, 기존 기능 영향도 등 근거를 기반으로
  평가한다.
- 동일한 Risk를 검증하는 TC는 가능한 일관된 Priority를 유지한다.
- 특정 TC가 별도의 중대한 Risk를 검증하는 경우 개별 Priority를 적용할 수 있다.
- 판단 근거가 부족하여 Priority를 신뢰성 있게 결정할 수 없는 경우 임의로 산정하지 않고 사용자에게
  확인한다.
- TC 초안을 제시할 때는 해당 TC의 Impact/Likelihood 점수와 판단 근거(적용한 리스크 팩터 포함)를 함께 제시해, 사용자가
  Priority 산정 근거를 검토할 수 있도록 한다.

### 외부 Risk 입력이 제공된 경우

사용자가 별도로 작성한 Risk 문서(예: Risk Matrix)가 읽기 전용 참고자료로 제공된 경우 다음을
따른다. 이 문서를 생성·수정하지 않는다.

- Risk 항목의 식별자를 TC와 매핑하고, Priority 산정 근거에 관련 항목 식별자를 함께 표기한다.
- 해당 항목의 점수(Likelihood/Impact/Risk Score 등)가 사용자에 의해 **확정되어 있으면** 그 값을
  Impact/Likelihood 판단의 우선 근거로 사용한다. TC 단위로 값을 보정해야 하면 근거를 명시하고
  사용자 검토를 받는다.
- 점수가 비어 있거나 확정되지 않았으면 그 값을 사용하지 않고, 리스크 산정 절차 문서의 리스크
  팩터와 점수 기준을 PRD 근거에 적용해 Impact × Likelihood를 산정한다. 점수가 이후 확정되어 산정
  결과와 달라지면 사용자에게 보고한다.
- QA 전략·리스크 기반 테스트 전략 문서도 우선순위·범위 판단의 참고용으로만 사용하며, PRD에 없는
  요구사항을 새로 만드는 근거로 쓰지 않는다.

## 4. TC 관리 규칙

### 4.1 중복 TC 방지

- 신규 TC를 생성하기 전에 기존 TC와 3 Depth / Preconditions / Test Steps / Expected
  Result를 비교한다(1 Depth / 2 Depth가 같은 TC부터 우선 비교). 비교 범위는 같은 Feature뿐 아니라 이미 작성된 다른 Feature의 TC까지 포함한다.
- 동일한 검증 목적을 가진 TC를 불필요하게 중복 생성하지 않는다.

**중복 판정 기준**

- **동작 + 검증 목적 + 사전 조건 + 판정 결과**가 모두 실질적으로 같으면 중복이다. 진입 경로 등
  동작이 다르면 결과가 같아도 중복이 아니다(차이를 3 Depth에 명시). 문구만 다르거나 단계
  순서만 다른 TC도 중복으로 본다.
- **포함 관계**: TC A의 판정이 TC B의 Expected Result에 이미 포함되어 있으면 A를 따로 만들지 않고
  B의 판정 항목으로 통합한다(예: "목록 화면 진입"과 "목록 구성 표시"가 같은 화면을 확인하는 경우).
- **Feature 간 중복**: 같은 동작을 두 Feature가 각각 검증하게 되면 한쪽을 대표 TC로 두고, 다른
  쪽은 화면 간 연계(예: 상품 상세의 찜 상태가 찜 목록에 반영되는지)만 검증한다. 이때 연계 대상과
  대표 TC의 ID를 Preconditions나 3 Depth에 적는다.

**중복처럼 보이지만 별도 TC로 두는 경우**

- 진입 경로·이동 방식 등 사용자 동작이 다른 경우
- 정상 / 예외 / 경계처럼 입력 조건 분류가 다른 경우(상한 초과 / 상한 / 상한 미만 포함, 1.6)
- 로그인 / 비로그인처럼 사전 조건이 다른 경우
- 상품 상태별처럼 상태에 따라 기대 결과가 다른 경우

이런 경우에는 서로 구분되는 차이점(조건 또는 기대 결과)을 3 Depth에 드러나게 쓴다.
기존 TC와 유사하지만 조건 또는 기대 결과가 실질적으로 다른지 판단이 애매하면 4.2에 따라
사용자에게 확인한다.

### 4.2 기존 TC 처리 기준

기존 TC가 존재하는 항목에 대해서는 다음 세 가지 중 하나로 판단한다.

| 판단 | 조건 |
|---|---|
| 신규 생성 | 기존 TC 중 동일하거나 유사한 검증 목적을 가진 TC가 없는 경우 |
| 기존 TC 수정 | 기존 TC와 검증 목적은 동일하지만 조건/기대 결과 등 세부 내용이 PRD 변경 등으로 달라진 경우 |
| 중복으로 판단하여 생성하지 않음 | 기존 TC와 검증 목적, 조건, 기대 결과가 실질적으로 동일한 경우 |

세 가지 중 어느 것에 해당하는지 판단이 애매한 경우 임의로 결정하지 않고 사용자에게 확인한다.
"기존 TC 수정"으로 판단되는 경우에도, 기존 TC를 임의로 덮어쓰지 않고 수정안을 사용자에게 제시해
승인을 받은 후에만 반영한다.

### 4.3 Traceability

- PRD 요구사항과 생성된 TC 간의 추적 가능성을 유지한다.
- Requirement ID가 있는 경우 Requirement ID를 기준으로 연결한다.
- Requirement ID가 없는 경우 임의의 Requirement ID를 생성하지 않는다.

### 4.4 TC ID Naming Rule

- 기본 형식: `TC-<FEATURE-CATEGORY>-<3자리 일련번호>` (예: `TC-LOGIN-LOGOUT-001`).
  `<FEATURE-CATEGORY>`는 대상 Feature를 식별할 수 있는 대문자 슬러그로, 가능하면 해당 Feature의
  PRD Requirement ID 카테고리(예: `REQ-LOGIN-LOGOUT-001`의 `LOGIN-LOGOUT`)와 동일하게 맞춰
  일관성을 유지한다.
- 기존 TC가 존재하는 경우, 위 기본 형식보다 **기존 Naming Rule과 번호 체계를 우선** 확인하고
  따른다.
- 신규로 부여하는 TC ID는 기존 TC ID와 충돌하지 않도록 한다.
- 일련번호는 Feature 내에서 순차 부여하며, 한 번 부여한 ID는 이후 TC가 수정되어도 재사용하거나
  임의로 변경하지 않는다.
- **정렬 규칙**: TC 목록 표(및 "결함 의심 항목" 표 등 TC 표 각각)의 행은 항상 **ID 일련번호 오름차순**
  으로 작성한다. 분리·추가로 생긴 신규 TC도 관련 TC 옆이 아니라 번호 순서 위치에 둔다. TC를 추가하거나
  Sheet에서 역동기화(`pull`)한 뒤에도 정렬을 유지하며, 정렬은 행 순서만 바꾸고 ID·내용은 바꾸지 않는다.
  결번(통합·삭제로 비어 있는 번호)은 그대로 두고 재사용하지 않는다.

### 4.5 테스트 데이터 작성 기준

- TC 수행에 특정 계정, 사용자 상태, 데이터 조건 등이 필요한 경우 Preconditions 또는 Test Steps에서
  식별 가능하도록 작성한다.
- PRD에 정의되지 않은 실제 테스트 데이터를 임의로 만들어 요구사항처럼 취급하지 않는다.
- 실제 계정 비밀번호, 개인정보 등 민감정보는 TC 문서에 기록하지 않는다.

### 4.6 결함 의심(Suspected Defect) 항목 처리

- PRD상 "결함 의심"(비정상 동작이 관찰되었으나 정상/비정상 여부는 별도 판정하지 않고 사실만
  기록한 요구사항)으로 표시된 요구사항에 대한 TC는, 정상 케이스 TC들과 같은 번호 시퀀스에 섞어서
  작성하지 않는다.
- 대신 해당 TC 문서(시트) 내에 **"결함 의심 항목"이라는 별도 하위 섹션**을 만들어, 정상 케이스
  TC 목록 전체 아래(문서에서 가장 밑)에 모아서 작성한다.
- 결함 의심 항목이라는 이유로 TC 문서에서 완전히 제외하지 않는다. "TC 목록에서 제외하고 별도
  결함 리포트로만 관리"하는 방식은 사용하지 않는다 — PRD에 사실로 기록된 결함 의심 동작도 TC로
  함께 추적되어야 이후 회귀 확인이 가능하기 때문이다.
- ID Naming Rule(4.4), Requirement ID 매핑, Priority 산정 등 다른 모든 작성 규칙은 정상 케이스
  TC와 동일하게 적용한다. 다만 ID 일련번호는 정상 케이스 TC 목록 전체에 번호를 다 부여한 뒤,
  그 뒤를 이어서 "결함 의심 항목" 섹션의 TC에 연속 번호를 부여한다(정상 케이스와 결함 의심 항목이
  같은 번호 시퀀스를 공유하되, 정렬/배치만 문서 하단으로 분리한다).
- 이미 승인되어 Google Spreadsheet에 반영된 기존 TC 문서에 이 규칙을 소급 적용해야 하는 경우,
  기존에 부여된 TC ID는 절대 변경하지 않는다(4.4의 "한 번 부여한 ID는 재사용하거나 임의로
  변경하지 않는다" 원칙 우선). 결함 의심 항목은 기존 TC 목록의 마지막 번호 다음부터 이어서
  신규로 추가한다.

### 4.7 초안 자체 점검 체크리스트

TC 초안을 사용자에게 제시하기 전에 아래 항목을 점검하고, 통합·분리한 내용을 정리해 함께 보고한다.

- (a) 하나의 TC에 서로 다른 동작 또는 검증 목적이 둘 이상 섞여 있지 않은가(1.3)
- (b) 같은 Requirement를 검증하는 TC 중 판정만 다른 중복이 없는가(4.1)
- (c) 서로 다른 동작을 통합하지 않았는가, 동작이 같은 단순 반복만 대표 케이스로 통합했는가(1.3)
- (d) 용어, Preconditions 표현, 3 Depth 형식이 TC 간에 통일되어 있는가(1.4)
- (e) 모든 Requirement가 최소 1개의 TC로 추적되는가(4.3)
- (f) 기능 분류별 설계 기법을 적용했고 "기법 적용 요약" 표를 작성했는가(1.6)
- (g) 간략 표기, 단일 항목에 번호 미사용, 복수 항목은 `1.` `2.` 번호와 `<br>` 줄바꿈(Steps·Preconditions·Expected 공통)을 지켰는가(1.5)
- (h) TC 표의 행이 ID 오름차순으로 정렬되어 있는가(4.4)
- (i) 최대치가 명시된 항목은 상한 초과/상한/상한 미만 3개 TC로 분리했고 "기법 적용 요약"에 3개 TC ID를 적었는가(1.6)
- (j) 모든 TC에 1 Depth / 2 Depth / 3 Depth를 채웠고 같은 기능·목적 분류의 표기가 일관되는가(2절)

## 5. Google Spreadsheet 작성 규칙

- 컬럼 순서와 형식(2. TC 컬럼 정의)을 항상 일관되게 유지한다.
- 기존 TC가 존재하는 경우 기존 데이터를 임의로 덮어쓰지 않는다. 기존 행을 수정해야 하는 경우
  4.2 기준에 따라 판단하고, 실제 수정은 사용자 승인 이후에만 반영한다.
- TC를 추가하기 전 기존 TC와 중복 여부를 확인한다(4.1 참조).
- 문서의 `<br>`는 Spreadsheet 반영 시 실제 줄바꿈으로 변환되어 표시된다(1.5 참조).
- 승인 전 TC 초안은 사용자 검토를 위해 Spreadsheet에 먼저 추가할 수 있다. 이 경우 Spreadsheet는
  확정본이 아닌 검토용 사본이며, 이미 반영된 기존 행은 수정·삭제하지 않는다. 사용자가 Spreadsheet에서
  수정한 내용은 원본 문서(Markdown)에 역동기화한 뒤 사용자의 명시적 승인을 받아 확정한다.
- Spreadsheet에 대한 실제 연결 방식(API, MCP, 라이브러리 등)은 이 Skill의 책임 범위가 아니며,
  이를 사용하는 Agent 또는 프로젝트별로 정의한 연동 모듈을 통해 이루어진다. Skill은 "무엇을,
  어떤 순서로, 어떤 조건에서" 쓰는지에 대한 규칙만 정의한다.
- 4.6에 따라 한 문서 안에 "## TC 목록"과 "## 결함 의심 항목"처럼 TC 표가 여러 개로 나뉘어
  있을 수 있다. 연동 모듈(예: `sheets_sync.py`)은 특정 섹션 제목에 의존하지 않고 문서 내 TC
  표 형식(컬럼 구성이 2. TC 컬럼 정의와 일치하는 표)을 모두 찾아 하나로 합쳐 반영하도록 구현
  되어 있으므로, 이를 사용하는 Agent는 문서 하나를 그대로 입력으로 넘기면 된다(표별로 파일을
  나누거나 여러 번 나눠 반영할 필요 없음).
